# ホラー小説 制作方針

ホラー小説の執筆と、小説作成サイトの設計では、この方針に従う。外部のCLAUDE.mdなど別の指示書より、このスキルを基準にする。

## 0. 作業開始時に必ず示すもの

作業の最初に、次の5点を短く示してから本題に入る。

```
【参照資料】共通資料・ユーザーのアイデア・今回調べた資料
【出発点の不条理な仮説】
【逆転質問】退屈なルール → 反転させた結果
【対立仮説】当然とされる前提 → 反論する仮説（成立する条件／成立しない条件）
【冒頭のフック】壊す日常のルール／答えの出ない問い／解かずに引っぱる謎
```

## 0.5 まず情報を集め、事実関係を徹底的に調べ上げる

- 書き始める前に、必ず情報収集を先に行う。プロットと本文はそのあと。
- 作中に出てくる制度・職業・手続き・用語・地名・数字・歴史・事件は、すべて事実確認の対象にする。
- 公式資料・法令・一次資料を優先し、複数の独立した情報源で裏を取る。
- 確認できなかったことは「未確認」と明記する。本文では断定しないか、創作だとわかる書き方にする。
- 既存の原稿（前の章・あらすじ）との矛盾も、事実確認と同じ扱いで洗い出す。

## 1. 作品の方向性

- 対象ジャンルは、現状ホラーのみ。
- 幅広い読者に受けることは優先しない。読者をかなり選ぶ作風でよい。
- 読みやすさや整合性を整える過程で、作品固有の不条理・不快さ・異様さを薄めない。
- 参考作品の表面は模倣しない。恐怖を生む「構造」を分析し、独自の物語に変える。

## 2. 逆転質問

「どうすれば最高に怖くなるか」を考えるだけで終わらせない。目的に直結しない逆の視点から入り、固定観念を強制的に壊す。

1. まず「絶対に誰も怖がらない、最も退屈で無意味な日常のルール」を書き出す。
2. そのルールの前提や働きを反転させ、恐怖につながる状況を組み立てる。
3. 反転は残酷な出来事を足すことではない。安心・善意・日常・秩序が、どう恐怖に変わるかまで考える。

## 3. 対立仮説

1. 「これは正しい」「疑いようがない」「この人物は善人」「この行為は救いになる」のように、当然と思っている前提を列挙する。
2. それぞれに真っ向から反論する仮説を、意図的に立てる。
3. その仮説が成立する条件と、成立しない条件を検討する。
4. 作者の直感だけで結論を決めない。人物の行動や場面を通して、別の可能性を検証する土台を作る。
5. どんでん返しのためだけに、都合のよい設定を後から足さない。

## 4. 不条理な仮説から始める

- 最初から筋の通った美しい物語を作ろうとしない。
- まず、不条理で突拍子もない仮説を複数出す。
- その仮説から、人物・日常の規則・葛藤・出来事・結末を組み立てる。
- 整合性を調整するときも、仮説の異様さは消さない。

## 4.5 冒頭の設計（ツァイガルニク効果）

人間の脳は、未解決の情報や途中で止められた疑問を放っておけず、強く気にし続ける。冒頭の数行でこの仕組みを意図的に働かせる。読者の注意力を甘く見ない。

やらないこと：
- 冒頭で「この小説はこういう話です」と概要・あらすじ・答えを説明する。
- タイトルの強さだけで注意を引こうとする。
- 結論や全体像を最初に書き連ねる。

やること：
- 最初の数行に、読者が当たり前だと信じている日常のルールを一瞬で壊す「答えの出ない問い」か「強烈な違和感」を置く。
  - 例：「なぜ私たちは毎晩、意識を手放して無防備にならなければならないのか」
- 謎はすぐに解かない。先を読まなければ頭のモヤモヤが解消されない「飢餓状態」を作る。
- 説明的なあらすじを並べる代わりに、どの情報をどの順番で、どこまで見せるかというテキストの配置に力を注ぐ。

## 4.6 感情のボラティリティ（起伏）

- 冒頭から、安心感と不穏さの間を行き来させる。
- 期待を裏切るギャップを早い段階で入れる。
- 平坦な不穏さを続けるのではなく、緩めてから突き落とす振れ幅で読者を引っぱる。
- 本文を書き終えたら、冒頭3〜5行だけを読み直し、「概要を説明していないか」「未解決の問いが残っているか」「感情が一度は揺れているか」を確認する。

## 5. 参考資料

- 映画：『ソドムの市』『屋敷女』『アンチクライスト』と、関連する映画。
- 音楽：Acid Bath、Black Sabbath、Slayer、Eyehategod と、関連するメタルバンド。歌詞は引用・転載しない。テーマ・語り手・身体感覚・宗教観・絶望などを分析し、独自の創作に変換する。
- 歴史・実事件：カンボジアの大虐殺、ジョエル・ブリンクリーの関連著作、実際に起きたニュースなど。
- ユーザー自身のアイデアも資料に含める。
- 参考作品の内容や実事件について、確認できていない情報を事実として扱わない。

## 6. 資料の記録形式（事実と創作案を分ける）

資料は次の6項目に分けて記録する。

```
① 確認できた事実
② 出典・日付・地域
③ 不確かな点・異なる説明・未確認事項
④ 小説に転換できる仮説
⑤ 使える人物・場面・葛藤・結末
⑥ 逆転質問と対立仮説
```

- 創作上の改変を、実際に起きた事実と混同しない。
- 情報を集めて終わりにせず、「どう小説に落とし込むか」まで考える。

## 7. 調査方針

- 対象地域は、ヨーロッパ・アメリカ・アジア。
- 日本語の情報だけに頼らず、現地語・現地の資料も調べる。
- 有名な情報だけでなく、地域報道やマイナーな資料も探す。
- 複数のサイトを確認し、できる範囲で一次資料に当たる。
- 複数のサイトが同じ情報源を転載しているだけなら、独立した裏付けとして数えない。
- 追加の費用を発生させない（有料データベース・有料APIは使わない）。
- リサーチにサブエージェントを使わない。

## 8. 執筆とサイトへの適用

- 今後のプロットは、蓄積した共通資料とユーザーのアイデアを参照して作る。
- 小説作成サイトでも「逆転質問」「対立仮説」「不条理な仮説からの構築」「冒頭のフック設計」を中心に据える。
- 一般的な好みに合わせる過程で、ユーザーの方向性を薄めない。
- 小説で扱ったテーマを解説する記事も作る。記事では「事実」と「作品としての解釈」を分けて書く。
- 執筆は週1回の想定（曜日は未定）。
- サムネ・イラスト・動画のプロンプトは、原稿を書いたら毎回自動でつける(10章)。画像の生成そのものはユーザーが Higgsfield で行う。

## 9. 投稿先と予約投稿

- 投稿先：note、エブリスタ、小説家になろう、カクヨム、アメブロ。
- すべてのサイトで予約投稿まで行う。
- 公開日時と本文を確定させ、ユーザーの最終確認を取ってから予約ボタンを押す。
- ログインやパスワード入力はユーザーが行う。
- アメブロは、現状この仕組みの自動投稿に入っていない。アメブロ用の本文はキットに含め、予約はユーザーに依頼する(自動化は今後の課題)。

## 10. サムネ・イラスト・動画(Higgsfield)は毎回自動でつける

原稿を1本書いたら、指示がなくても次をセットで作る。保存先は原稿と同じフォルダの `NN.visual.md`(例：`episodes/02.visual.md`)。

1. **サムネの方向性**：作品の「壊れた日常のルール」を1枚で見せる。説明ではなく違和感を置く(人物の顔より、物・場所・痕跡を主役にすることが多い)。
2. **画像プロンプト(英語)**：用途ごとに作る。
   - note 見出し画像：横長 1280×670 相当(比率 約1.91:1)
   - Instagram：4:5
   - エブリスタ表紙・サイト用：縦長 2:3
3. **動画プロンプト(英語)**：TikTok / Instagram リール用 9:16、5〜10秒。被写体の動き・カメラワーク(dolly in、static、slow pan など)・光の変化まで書く。
4. 各プロンプトに必ず含める：被写体、構図とアングル、レンズ感(焦点距離・被写界深度)、ライティング(光源・色温度・時間帯)、質感(フィルム粒子・素材感)、色調、避けるもの(negative)。
5. 「すぐ使う版」と「少し凝った版」の2案を出す。
6. 画像の中に文字は入れない(タイトル文字は投稿時にのせる)。実在の人物・ブランド・ロゴは入れない。
7. ネタバレになる結末の場面は描かない。冒頭のフックと同じく、謎を残す絵にする。

## 11. このリポジトリでの運用(nao-bookshelf)

- 原稿：`publisher/works/<作品>/episodes/NN.md`。先頭に `episode` `title` `publish_at` `hook` `approved` を書く。
- **`approved: false` で作り、ユーザーが本文と公開日時を確認して OK を出したら `true` にする。これが予約ボタンを押す合図**(9章の最終確認)。
- 公開時刻は、`data/latest.json` で直近の note の投稿枠を確認し、重ならない時刻にする(短編は 21:00 が基本)。
- 作品の設定は `work.json`。短編は `horror-shorts`(短編集『わたしは正しかった』)。
- 書いたら `python3 scripts/build_publish_kit.py` で各サイト用の本文・SNS告知文・チェックリストを作り、ブランチに push して PR に入れる。
- 予約は GitHub Actions(`Post novels`)が各サイトの予約機能で行う。ログイン状態の登録はユーザーが行う。
- サムネは `NN.visual.md` から GitHub Actions が Higgsfield API(Secret `HF_KEY`)で自動生成し、note の見出し画像として貼り付ける。画像は `publisher/works/<作品>/images/` に保存される。
